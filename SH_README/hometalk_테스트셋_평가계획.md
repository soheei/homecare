# 홈톡 테스트셋 준비 + 정확도 평가 계획

작성일: 2026-10-13 (계획 문서 — 아직 녹음·구현 전)

## Context
- ESC-50(시중 음원)으로 잡은 YAMNet 임계값이 Pi 마이크 실녹음에서는 크게 어긋났다 (`door_visitor` 0.35→0.7, `door_security` 0.35→0.6 등). 즉 **공개 데이터셋 점수는 제품 정확도가 아니다.**
- 현재 평가 자산: `yamnet/verification/evaluate.py`(ESC-50 fold 1–4 스윕, fold 5 holdout, 카테고리당 양성 8개뿐), 벤치마크용 비디오/오디오 라벨 데이터는 **없음**. 비전은 합성 입력 단위 테스트뿐. 신호버스·평가도구(`SH_README/hometalk_테스트_TODO.md` §5)는 미구현.
- 목표: 논문/발표에서 "우리 제품의 정확도"라고 말할 수 있는 근거(실녹음 테스트셋 + 표준 지표)를 만든다.

## 질문에 대한 답 (요약)
1. **논문에는 Pi 실녹음으로 평가해야 하나? → 예.** 제품 정확도 주장은 배포 조건(같은 Pi·마이크·방)의 데이터로만 성립. ESC-50은 "사전 검증/비교 기준(baseline)"으로만 쓰고, 둘의 차이(도메인 갭)를 그대로 결과로 보고하면 오히려 기여가 된다.
2. **임계값 튜닝셋 ≠ 평가셋.** 이미 임계값을 실녹음에 맞춰 바꿨다면, 그 녹음으로 다시 평가하면 점수가 부풀려진다(데이터 누수). 튜닝용(dev)과 최종 평가용(test)을 **세션 단위로** 분리하고 test는 임계값 확정 후 1회만 돌린다.
3. **얼마나?** 아래 표 기준. 통계적 불확실성은 점수에 **95% 신뢰구간**(Wilson)을 병기해서 "N이 작음"을 정직하게 표시한다.
4. **지표:** 붙여넣은 논문 방식 그대로 — TP/FP/TN/FN → Precision, Recall, F1, Accuracy, MCC, ROC-AUC. 단, 홈 모니터링은 불균형(대부분 무사건)이라 **Accuracy는 참고용**, 주지표는 Recall(놓침)·Precision·F1·MCC·**시간당 오경보 수(FA/h)**.

## 1. 평가 단위 정의 (먼저 고정)
- **오디오:** 사건 단위. 정답 = "사건 발생 시각 ±3초 안에 해당 카테고리 이벤트가 전송됨". 무사건 구간에서 전송된 이벤트 = FP. 판정은 YAMNet 점수가 아니라 **실제 파이프라인 출력(`event_rules.py` 규칙 + 쿨다운 적용 후)** 기준 — 제품 정확도이므로.
- **비전:** 클립 단위(시나리오 1개 = 1클립, 사건 있음/없음) + 무사건 장시간 영상의 FA/h.
- **융합:** 같은 시나리오를 소리 단독 / 영상 단독 / 융합(`confirmed` vs `single`)으로 비교 (TODO §5 계획과 연결).
- **Claude 브리핑/Q&A:** 사실 정확도(환각 여부) 별도 평가 (§6).

## 2. 오디오 테스트셋 (Pi 마이크 실녹음)
라벨 카테고리: `fire_alarm_siren`, `glass_impact`, `baby_cry`, `scream_shout`, `door_visitor`, `door_security`, (`animal`). `fall_suspect`는 `AUDIO_DISABLED_CATEGORIES`라 오디오 평가 제외(영상으로).

| 항목 | 최소(발표용) | 권장(논문용) |
|---|---|---|
| 카테고리당 양성 사건 | 30 | 50–100 |
| 서로 다른 소스(예: 초인종 3종, 아기울음 음원 5종) | 3 | 5+ |
| 녹음 세션 수 (날·시간대 분산) | 2 | 3+ |
| 거리/방향 | 근·중·원 3단계 | 동일 |
| 소음 조건 | 조용/TV/대화/청소기·주방 | 동일 |
| 음량 | 작게·보통·크게 | 동일 |
| **음성(무사건) 배경** | 총 2–3시간 | 10시간+ (생활소음 포함) |

- 음원 재생 방식: 스피커로 공개 음원을 재생해 Pi 마이크로 녹음하면 효율적(재생 음원 종류·거리·음량을 변수로 체계적 변화). 단 일부(초인종·노크·문 소리)는 **실제 소리**도 섞는다 — 스피커 재생만으로는 실환경 일반화를 주장하기 어렵다.
- 비명·낙상 충격음은 사람이 직접 내기 부담/위험 → 공개 음원 재생 + 최소 일부 실연(안전하게)으로 구성.
- 음성 배경은 **사건이 없는 일상** 녹음이 핵심(FA/h 산출). 사람 말소리, TV, 설거지, 청소기 등 오경보 유발 소음을 의도적으로 포함.
- 저장: 원본 WAV를 그대로 녹음(16kHz mono)하고, 라벨 CSV `edge/data/eval/audio_labels.csv` (컬럼: `file, session, category, onset_s, offset_s, source_id, distance_m, noise_cond, volume, split(dev|test)`). 개인 음성이 섞이면 공개 저장소에 커밋 금지(.gitignore, 로컬/별도 보관).
- **split:** 세션 단위로 dev(튜닝)/test(최종). 예: 세션 1–2=dev, 세션 3=test. 같은 음원 파일이 dev/test에 양쪽에 들어가지 않게 한다.

## 3. 비전 테스트셋
시나리오(각 클립 10–30초, 조명 2종 이상):
- 방문자 `visitor_detected`: 접근→3초 이상 정지/통과만(비방문) 구분. 양성 30, 음성(지나가기·가족 오가기·반려동물·그림자) 30.
- 택배 `delivery_suspect`: 박스 두기 양성 30 (박스 색: 바닥과 비슷한 색 포함 — 알려진 약점 `DIFF_THRESHOLD=35`), 음성(물건 잠깐 들었다 놓기, 조명 변화, 카메라 흔들림) 30.
- 낙상 `fall`: 낙상 양성 30(안전 매트, 앞/옆/뒤 방향), 음성 30(앉기·눕기·줍기·운동) — 현재 `test_fall_detector` 5건 실패 상태이므로 **개선 전 baseline을 지금 먼저 측정**(TODO §3-4와 일치).
- 무사건 장시간(1–2시간, 낮/밤) → FA/h.
- 라벨 CSV: `edge/data/eval/video_labels.csv` (`file, scenario, label, start_s, end_s, lighting, split`). 얼굴 등 개인정보 → 커밋 금지.

## 3-B. YOLO 평가 상세 (3층 구조로 나눠서 평가)
현재 코드: `yolov8n.pt`(COCO 사전학습, **재학습 없음**), `class_id==0`(person)만 사용, `YOLO_CONFIDENCE=0.5`, 5fps, 640×480. 택배는 YOLO가 아니라 배경 차분(`delivery_detector.py`)이다. 즉 "YOLO 정확도" 하나로 뭉뚱그리면 안 되고, 어디서 틀렸는지 분리해야 한다. YAMNet처럼 "공개 벤치마크(COCO) 점수 ≠ 우리 카메라 점수"가 그대로 적용된다 (Pi 카메라 화각·저조도·압축·현관 역광).

**층 1 — 검출기 자체 (사람 박스)**
- 목적: 우리 카메라 환경에서 yolov8n이 사람을 얼마나 잘 찾는가.
- 데이터: 시나리오 영상에서 프레임 샘플링(예: 영상당 2fps 추출, 총 **300–500프레임**, 조명·거리·자세(서기/걷기/앉기/누움/가려짐) 분산) → 사람 박스 수동 라벨(CVAT/LabelImg/Roboflow, YOLO txt 형식). 사람이 없는 프레임 100+개 포함(FP 확인).
- 지표: IoU 0.5 기준 Precision/Recall/F1, AP50(+ mAP50-95는 참고). 신뢰도 임계값 스윕(0.2–0.8)으로 PR 곡선 → 현재 0.5가 적절한지 판단. 자세별(특히 **누운 자세** recall)·조명별로 분해 — 낙상 판정의 전제이기 때문.
- 분할: 영상(세션) 단위로 dev/test 분리. 같은 영상의 프레임이 양쪽에 들어가면 누수.
- 비교(선택): yolov8n vs yolov8s — 같은 test로 Pi에서의 추론 속도(FPS)와 정확도 trade-off 표. 재학습(fine-tuning)은 **새 의존성/큰 작업이라 이번 범위 제외**, 필요하면 후속 제안.

**층 2 — 이벤트 규칙 (YOLO 출력 위의 로직)**
- 방문자(`VISITOR_REQUIRED_FRAMES=15`), 낙상(`FALL_DROP_THRESHOLD=35px` 등)은 검출 박스 위의 규칙이라 층 1이 완벽해도 틀릴 수 있다. 3절의 클립 단위 시나리오로 평가하고, 오류를 원인별로 분류: ① 검출 실패(박스 없음) ② 규칙 임계값 문제 ③ 추적 불안정(ID 바뀜). 이 분류표가 "무엇을 고쳐야 하는가"를 알려준다.
- 낙상은 픽셀 기준이라 사람 크기/거리에 따라 달라짐 → 거리 3단계(가까/중간/먼)별 결과 분리. (정규화 개선은 별도 작업, 여기선 baseline 측정만)
- 택배: 배경 차분 방식이므로 YOLO 평가에서 분리해 별도 항으로 보고(박스 색 대비, 조명 변화 FP).

**층 3 — 종단 간(end-to-end)**
- 영상 → 파이프라인 → 전송된 이벤트(DB 기록)까지 시나리오별 TP/FP/FN, 무사건 장시간 FA/h, 지연(초). 소리와의 융합 비교(소리 단독/영상 단독/융합)도 이 층에서.

**Pi 실기 조건 필수:** 노트북 웹캠 아닌 **실제 Pi 카메라·실제 설치 위치**에서 촬영. 추론은 Pi에서 돌린 결과(프레임 드롭·FPS 저하 포함)를 사용. 개인 얼굴 영상은 커밋 금지.

**YOLO 도구:** `vision/eval_detector.py` — 라벨(YOLO txt) + 프레임 → 예측 → IoU 매칭 → P/R/AP50, 신뢰도 스윕 CSV. (ultralytics가 이미 의존성이라면 `model.val()` 재사용 가능 — **확인 필요**; 없는 의존성은 추가하지 않음.)

## 4. 임계값 튜닝 절차 (dev 한정)
1. dev 녹음을 `yamnet`에 통과시켜 프레임 점수 캐시(`threshold_strategy_common.py`의 캐시 구조 재사용).
2. 카테고리별 임계값 스윕 → F1(또는 위험 카테고리는 F2: 놓침 우선) 최대 지점 선택. 위험(`danger`) 카테고리는 Recall 우선, 방문자·문 소리는 FP 억제 우선(알림 피로).
3. 선택값을 `yamnet/core/event_rules.py`에 반영 (Plan §9에서 "미반영"이던 부분 정리).
4. 임계값 **동결** → test 세션에서 1회 평가.

## 5. 지표·보고 형식
- 카테고리별 혼동행렬 (TP/FP/FN/TN) + P/R/F1/MCC + Wilson 95% CI, 전체는 macro-F1.
- ROC-AUC/PR 곡선은 점수 기반이 가능한 오디오 프레임 단계에서 산출 (규칙 이후 이벤트 단위는 임계값 하나의 점이라 AUC 불가 → 이 차이를 명시).
- FA/h(오경보/시간), 지연(사건→전송 초), 쿨다운으로 인한 누락 별도 집계.
- 비교표 3종: (a) ESC-50 holdout vs Pi 실녹음 test (도메인 갭), (b) 임계값 튜닝 전/후, (c) 소리 단독/영상 단독/융합.
- 한계 명시: 단일 Pi·단일 방, 스피커 재생 비중, 소규모 N. 재현 위해 녹음 조건 문서화.
