# 홈톡 YAMNet 실녹음 평가 계획

작성일: 2026-10-21 (2026-10-13 초안을 다시 씀 — 이번 개정은 **오디오(YAMNet) 평가만** 다룬다. 비전·융합·Claude Q&A 평가 초안은 git 이력의 이전 버전(`819f721` 시점)에 남아 있고, 오디오 평가가 끝난 뒤 별도 문서로 다시 세운다.)

## 1. 목적
1. **(핵심) Pi로 녹음한 소리를 들려줬을 때 이벤트를 제대로 인식하도록 카테고리별 임계값을 다시 정한다.** ESC-50(`yamnet/ESC-50`, 시중 음원)으로 정한 임계값은 Pi 마이크 녹음에서는 판단이 다르게 나왔다(`door_visitor` 0.35→0.7 등). **공개 데이터 점수 ≠ 제품 정확도.**
2. 그렇게 정한 판정 코드(YAMNet + `core/event_rules.py`)가 Pi 실녹음에서 얼마나 맞는지 표준 지표로 검증한다.

## 2. YAMNet은 회귀인가 분류인가 → **분류 모델 (다중 라벨)**
- 입력: 16kHz mono 파형 → 0.96초 창을 0.48초씩 밀며 프레임화.
- 출력: 프레임마다 AudioSet **521개 클래스 각각의 확률(0~1)**. 마지막 층이 softmax가 아니라 **sigmoid**라 클래스끼리 독립(합이 1이 아님) → "Speech 0.8 + Music 0.6"처럼 동시에 높을 수 있다.
- 숫자를 예측하는 회귀가 아니다. 모델은 *점수*만 내고, "이벤트다/아니다"는 우리 규칙(`event_rules.py`: 임계값·다수결·조합)이 정한다. 따라서 **이진 분류 지표**로 평가한다.
- 노트북 2번 섹션에서 "프레임별 521개 점수 합 ≠ 1"을 데이터로 직접 확인한다.

## 3. 평가 단위와 방식
- **클립 단위 one-vs-rest 이진 분류.** 카테고리 `c`를 평가할 때 양성 = `c`로 녹음한 클립, 음성 = 다른 카테고리 클립, 예측 = `c`의 규칙이 그 클립에서 한 번이라도 `triggered`.
- 판정은 YAMNet 점수가 아니라 **규칙을 거친 출력**(제품이 실제로 "이벤트"라고 보내는 결과)으로 한다. 쿨다운은 15초 클립 평가에서는 영향 없어 제외.
- 사건 시각(onset) 라벨이 없으므로 프레임·시간 단위 평가와 ±3초 지연 평가는 **아직 불가**(녹음 시작 후 소리를 낸 시점을 기록하지 않음).

## 4. 현재 데이터 (`yamnet/dataset/`, `record_dataset.py`로 Pi 녹음)
| 카테고리 | 클립 | 비고 |
|---|---|---|
| fire_alarm_siren | 3 | |
| glass_impact | 3 | |
| baby_cry | 3 | |
| scream_shout | 3 | |
| door_visitor | 6 | 폴더 5개 (door_visitor2에 2개) |
| animal | 6 | 고양이 3 + 강아지 3 (규칙이 한 카테고리로 봄) |
- 전부 15초·16kHz·mono·위치 center, 2026-10-18 오전 한 세션, 24클립. 폴더 이름 = 정답 라벨, 끝 숫자 = 같은 이벤트의 **서로 다른 음원 번호**(2026-10-21 확인). 좌/우 임의 배치·음량 변경으로 녹음했으나 JSON `position`은 전부 `center`, 음량 기록 없음 → **위치·음량별 분석 불가**.
- `door_security`는 소리로 판단할 이벤트가 아니라고 결정해 **오디오 평가에서 제외**(2026-10-21). `fall_suspect`는 오디오 비활성, `long_silence`·`kitchen_risk` 등은 짧은 클립으로 평가 불가 → 제외.
- 저장소 규칙: `yamnet/dataset/*`와 `yamnet/output/`는 `.gitignore` 처리됨(개인 음성 가능성, 커밋 금지).

## 5. 평가지표 (노트북에서 직접 구현 — sklearn 미설치, 새 의존성 추가 없음)
| 지표 | 정의 | 왜 보나 |
|---|---|---|
| 혼동행렬 TP/FP/FN/TN | 카테고리별 2×2 + 카테고리×규칙 트리거 행렬 | 어느 소리가 어느 규칙을 잘못 울리는지 |
| **Recall** (+ Wilson 95% CI) | TP/(TP+FN) | 위험 소리를 **놓치지 않는가** (주지표) |
| **Precision** | TP/(TP+FP) | 울린 것 중 진짜 비율 = 알림 피로 |
| **F1 / F2** | P·R 조화평균 / Recall 2배 가중 | 위험 카테고리는 F2(놓침이 더 치명적) |
| **MCC** | −1~1 상관계수 | 클래스 불균형(음성이 훨씬 많음)에 강함 |
| Specificity, Accuracy | TN/(TN+FP), 전체 정답률 | **Accuracy는 참고용** (전부 "아님"이라 해도 높게 나옴) |
| **ROC-AUC** | 임계값과 무관한 구분 능력 | 임계값 탓인지 모델 탓인지 분리 |
| macro / micro 평균 | 카테고리 단순 평균 / 합산 | 전체 한 줄 요약 |
- ROC-AUC용 연속 점수 = "그 클립이 트리거되는 **가장 높은 임계값**"(규칙이 임계값에 단조라서 가능). 규칙 출력만으로는 점 하나뿐이라 AUC를 못 그리므로 이 차이를 보고서에 명시.
- 아직 못 재는 지표: **시간당 오경보(FA/h)**, 진짜 특이도 — 사건 없는 배경 녹음이 필요(§8).

## 6. 평가 절차 (노트북 `yamnet/yamnet_realworld_eval.ipynb`)
1. 데이터 로드·녹음 품질 점검(피크·RMS·포화·샘플레이트).
2. YAMNet 추론(프레임 점수 캐시 → 재실행 시 TF 불필요) + 분류 모델임 확인.
3. **제품 기준 평가 = 본 결과.** 현재 코드의 고정 임계값 그대로 지표·혼동행렬.
4. 임계값 스윕·ROC (**참고용, 낙관적** — 같은 데이터로 최적값을 고르므로 부풀려짐).
5. 음원 단위 교차검증(Leave-One-Source-Out): 음원 번호를 하나씩 빼고 나머지로 같은 선택 절차 재현. 같은 날·장소 녹음이고 음원이 3~5개뿐이라 **약식**.
6. 오류 분석: FN은 "YAMNet이 못 알아봄 vs 규칙이 걸러냄", FP는 "YAMNet이 그 소리를 무엇으로 불렀나".
7. 임계값·클래스 구성 재설정(§6-B) + ESC-50 2000클립 재검증 → 8. 교차검증 → 9. 보고서용 그림 8종 → 10. 음원별 분해 → 11. 오류 분석 → 12. CSV 저장(`realworld_final_thresholds.csv`, `realworld_variant_comparison.csv`, `realworld_eval_summary.csv`, `realworld_eval_clips.csv`).
- 실행: `yamnet/` 폴더의 노트북을 TensorFlow가 있는 커널에서 순서대로. 처음 한 번 TF Hub에서 모델을 받는다. 필요 패키지: `pandas`, `matplotlib`, `ipykernel`(현재 프로젝트 Python 3.10에는 미설치 — **설치는 사용자가 결정**).

## 6-B. 임계값·클래스 구성 재설정 방법 (노트북 6~8번 섹션)
- **Pi 녹음 = 선택 기준, ESC-50 전체 2000클립 = 오경보 방어선.** 사건 없는 배경 녹음이 없어, 임계값을 낮출 때의 오경보를 ESC-50 음성 클립으로 대신 점검한다.
- 규칙: ① 임계값 하한 0.15(배경 소음 미검증 영역 배제) ② ESC-50 음성 오경보율 ≤ 3% 인 값만 후보 ③ 후보 중 Pi F-점수 최대(위험도 `높음`은 F2, 나머지 F1) — 동점 구간에서는 ESC-50 Recall 이 5%p 넘게 떨어지는 값을 빼고 가운데 값 ④ 클래스/규칙 변형(예: 전화벨 클래스 추가)은 Pi 점수가 0.05 이상 오를 때만 채택.
- 검증: 음원 단위 Leave-One-Source-Out 교차검증으로 같은 선택 절차를 재현(처음 듣는 음원에서의 성능, 낙관성 점검).
- 산출물: Before/After 표, 변형 비교표, 보고서용 그림 8종(`yamnet/output/figures/`), CSV 4종. **`event_rules.py`는 노트북이 고치지 않고 사람이 옮긴다.**
- 조치 기준: Pi Recall ≥ 0.8 적용 가능 / 0.5~0.8 조건부 / 그 미만·검출 불가 보류.
- 한계: After 의 Pi 점수는 같은 데이터로 고른 값이라 낙관적. 반영 후 **새 세션**으로 고정 임계값 평가를 1회 해야 진짜 성능이다.

## 7. 결과 해석 원칙 (논문·발표용)
- 본 성능 주장은 §6-3(고정 임계값) 또는 교차검증 수치로. §6-4 최적 임계값 점수는 "후보"로만.
- 표본이 작다(양성 3~6, 1세션) → **모든 수치에 신뢰구간 병기**, "클립 수가 적어 불확실성이 크다"를 같이 쓴다.
- ESC-50 holdout 점수와 나란히 두고 **도메인 갭(공개 음원 vs Pi 마이크)** 자체를 결과로 보고하면 오히려 기여가 된다.
- 임계값 튜닝셋과 최종 평가셋은 **세션 단위로 분리**, test는 임계값 동결 후 1회만.

## 8. 부족한 데이터 → 다음 녹음 (우선순위)
1. **사건 없는 배경 녹음 2~3시간**(말소리·TV·설거지·청소기 등 오경보 유발 소음 포함) → FA/h, 특이도. *가장 큰 공백.*
2. **새 세션**(다른 날·시간대·거리·음량)을 test로 따로 보관 — 현재 24클립은 dev 용도.
3. 카테고리당 양성 **30개 이상(최소) / 50~100(논문용)**, 서로 다른 음원 3종 이상.
4. 초인종·노크 등은 스피커 재생 외에 **실제 소리**도 포함(재생음만으론 일반화 주장 어려움).
5. `scream_shout`(사람 실연, 안전하게) 등 클립이 적은 카테고리 보강.
6. 녹음 시 위치 인자(`left|right`)와 `--note`에 거리·음원·음량을 **기록**하고, 가능하면 소리를 낸 시각(onset)을 기록 → 이후 사건 단위·지연 평가 가능.

### 8-B. 핸드폰 재생 → Pi 재녹음 점검 (경로 손실, 2026-10-21 추가)
- `yamnet/playback_samples/`(ESC-50에서 이벤트별로 점수 높은 55클립, `manifest.csv` 포함)를 핸드폰으로 틀어 Pi로 다시 녹음 → `yamnet/dataset_phone/`. 라벨 `fire_alarm_siren01~15`, `glass_impact01~10`, `baby_cry01~10`, `door_visitor01~10`, `animal_dog01~05`, `animal_cat01~05`, `--note`에 `음량=작게|중간|크게`, 위치 left/right 기록.
- 노트북 12번 섹션이 같은 클립의 ESC-50 점수와 Pi 점수를 짝지어 점수 하락·음량 갭·음량/위치별 검출률을 낸다(그림 9·10). 쉬운 소리만 골랐으므로 **상한선 점검용이며 성능 수치가 아니다.**

## 9. 일정(제안)
1. (완료) 평가 노트북 작성·코드 경로 검증 — 가짜 점수로 전 셀 실행 확인, 실제 모델 실행은 사용자 PC에서
2. (0.5일) 노트북 실행 → 현재 24클립 결과 확인, 오류 분석
3. (1~2일) 배경 녹음 + 새 세션 녹음
4. (0.5일) 노트북 권장 임계값 → `event_rules.py` 반영(사람이 직접) → 동결
5. (0.5일) test 1회 평가, ESC-50 대비표 작성
